Environment audit

A full, read-only audit of the environment as it is now: platform, capacity, every volume, snapshot, backup and instance, and the findings: what is wrong, stuck, orphaned or close to a limit. Needs an administrator account.

Pre-flight checks and gate

Every prerequisite is checked before a migration may start. A check that fails blocks the gate and must be fixed. A check that warns or could not be verified needs an attestation: a named person's recorded statement with the evidence. Two different people then sign off. Only an open gate lets a migration start.

Needs the platform detected and the inventory read.

Select what to migrate, and how

Nothing is all or nothing. Choose volumes one by one, by group (class, project, attachment, size, snapshots, host, instance, workload risk), or any mix. Only volumes the pre-flight admitted can be chosen; a held-back volume shows why. By default every admitted volume is selected except those that needed a risk clearance. The settings below start at their safe defaults and can only be made stricter than the process minimum. Project names appear after you run the audit (tab 4).

Workload risk

Volumes that host something that may break (for example a legacy Windows server, or no guest agent) are not moved until two different people clear them. The check reads hints only (image properties, instance data, names) and cannot see inside a guest: a volume with no hint is not declared safe. Mark any volume the customer knows to be a risk.

Move volumes

Class A and B volumes are moved by Cinder itself: OpenMove locks the instance, sends one retype with on-demand migration, follows it, checks the result against the before-state and unlocks. It needs only the OpenStack APIs. Class C volumes are copied to the target through the data mover, image by image and checked, and then switched over. Always run the dry run first: it reads the cloud and lists the exact calls, and changes nothing.

A real run needs three things: a recorded lab validation of the OpenStack release (gate G0), an approved pre-flight gate, and no halt. Class C volumes (snapshots that stay) are moved too, by the staged method, once a migration host and a Cinder host are registered and ready on the Hosts tab; until then they are held back.
Phase 0: the lab tests

The playbook's lab tests (T1 to T22) and four that OpenMove adds (M1 to M4). OpenMove cannot run them: they need real hosts and people. Do each test, then record its result with what you did and saw. Gate G0 can be recorded from these results once every test of the retype path has passed for this release. Tests of the staged method (class C) are listed but not required while it is not built.

Reports

Word documents built from the same data the tool holds, so a report cannot disagree with what the tool knows. The pre-migration report lists every pre-flight check, the volumes to move and those held back, the gate and the sign-off, and includes the environment audit as a separate part.

During and after the run

The update report and the after report compare every volume the run touched with the state recorded before its cutover, and mark each difference as expected (back-end and volume type) or unexpected. The volume list is the same data as a spreadsheet.

The pre-migration report and the not-migrated report need the pre-flight to have run; the audit report needs the audit.

      Hosts

      Class C volumes (volumes with snapshots that stay) are copied by a small program, the data mover, on a Linux migration host that sees both back-ends' storage. A Cinder host runs the Cinder helper that creates the destination record. One host can do both. OpenMove logs in over SSH with its own key and only to a host whose key you have checked. The one use of a password is the setup of a new host (below); it is not kept. OpenMove places the mover itself and removes it again.

      OpenMove's public key

      Add this line to ~/.ssh/authorized_keys of the login user on each host. It is the only credential OpenMove keeps; a password is used only to set up a new host and is never saved.

      
      
      
    
      
    
      
      Set up a new host from here
      
      Prepare a Linux host on the customer network (it must see the arrays' storage network), then give OpenMove its address and the administrator login. OpenMove logs in once with the password, installs its own key, prepares the host (packages, a service account, narrow sudo rights, sshd), sets up the storage paths you describe below (iSCSI initiator, multipath, logins to the arrays), registers the host and checks it. The password is used for this setup only. It is not saved, not written to the journal or a log, and not left on the host. After the setup OpenMove uses only its key. The setup can be run again; every step looks first and changes only what differs.

      Diagnostics
      
    
      If anything goes wrong, a support bundle holds everything needed to find the fault without access to this site: the journal, every step with its intent and result, every call to the cloud and to the hosts with the complete output, the log, and what each host reports about itself. OpenMove also writes one by itself when it halts or meets an unexpected error.
